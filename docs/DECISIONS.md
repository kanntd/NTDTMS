# NTD TMS Decisions

บันทึกข้อตกลงที่ยืนยันแล้ว เพื่อป้องกันการออกแบบย้อนแย้งเมื่อเริ่มงานจากแชตหรือเครื่องใหม่ เพิ่มรายการใหม่พร้อมวันที่เมื่อมีการตัดสินใจที่เปลี่ยนพฤติกรรมระบบ

## Architecture

- ใช้ React + Vite + TypeScript สำหรับ internal desktop web app
- ใช้ Supabase เป็นแหล่งข้อมูลกลางและใช้ Cloudflare Pages/Worker/R2 สำหรับเว็บและไฟล์
- ใช้ Modular Monolith ไม่แยก microservices ในระยะนี้
- การทำงาน demo และ production ต้องแยกชัดเจน

## Customer, Product And Pricing

- ค้นหาและเลือกผู้รับก่อนผู้ส่ง
- ผู้ส่งที่แสดงอันดับแรกต้องเป็นผู้ส่งที่จับคู่กับผู้รับรายนั้นเท่านั้น จากนั้นจึงค้น master กลางหรือเพิ่มใหม่
- สินค้าที่แสดงต้องมาจากคู่ผู้รับ-ผู้ส่ง ไม่ปนสินค้าของผู้ส่งหรือคู่รายอื่น
- สินค้าและหน่วยนับเป็น master กลาง ไม่ผูกชื่อสินค้าเป็นรายการซ้ำต่อร้านค้า
- ราคามาตรฐานผูกกับ `ผู้รับ + ผู้ส่ง + สินค้า + หน่วยนับ` และเก็บประวัติเวอร์ชัน
- เปลี่ยนราคามาตรฐานไม่ย้อนแก้บิลเก่า
- ส่วนลดเฉพาะบิล เช่น 100 เหลือ 80 ต้องบันทึกส่วนลด 20 และราคามาตรฐานยังเป็น 100
- ถ้าต้นทางไม่ทราบราคา ให้ทำคำขอราคา รายการใหม่ของคู่เดิมต้องขึ้นสถานะขอราคาอัตโนมัติจนกว่าจะยืนยัน
- เมื่อยืนยันคำขอราคา ให้อัปเดตบิลที่ยังรอราคาและเปิดตั้งแต่บิลต้นทางของคำขอนั้นเป็นต้นไปตามกฎ workflow
- การปรับราคาหลายรายการรองรับเพิ่ม/ลดเป็นจำนวนเงินหรือเปอร์เซ็นต์ และต้องมีเงื่อนไขกรอง

## Payment

- มี 4 ประเภท: เงินสดต้นทาง เงินสดปลายทาง เครดิตต้นทาง เครดิตปลายทาง
- การจับคู่ผู้รับ-ผู้ส่งครั้งแรกต้องให้พนักงานเลือกประเภทชำระเงินเอง
- ครั้งต่อไปใช้ค่า default ของคู่นั้นแต่แก้ได้รายบิล
- เครดิตใช้รอบวางบิลสิ้นเดือนเป็นค่าเริ่มต้น
- หัก ณ ที่จ่าย 1% เป็นตัวเลือก ไม่ติ๊กให้อัตโนมัติ
- ไม่มี VAT ใน workflow ปัจจุบัน

## Loading And Trips

- ต้องเลือกสาขาปลายทางก่อนดูบิลรอขึ้นรถหรือสร้างเที่ยวรถ
- บิลเดียวแบ่งขึ้นรถหลายคันหรือหลายวันได้ตามจำนวนคงเหลือ
- บิลเดียวกันเพิ่มได้หนึ่งครั้งต่อเที่ยวรถ; การเพิ่มซ้ำในเที่ยวเดียวต้องถูกปฏิเสธและนับจำนวนบิลเพียงครั้งเดียว
- หากบิลยังเหลือ สามารถเพิ่มส่วนที่เหลือเข้าเที่ยวรถคันอื่น และแต่ละเที่ยวต้องนับบิลนั้นในยอดบิลของตัวเอง
- ตารางแสดงทะเบียนรถเป็นตัวระบุหลัก ไม่จำเป็นต้องแสดงเลขเที่ยวให้พนักงานในจุดที่ขอไว้
- ใบคลุมรถเรียงอำเภอเมืองก่อน แล้วเรียงผู้รับ ก-ฮ พร้อมแสดงจำนวนที่ขึ้นจริงสำหรับรายการบางส่วน

## Destination And Delivery

- สาขาปลายทางมองเห็นเฉพาะข้อมูลของสาขาตนเอง ยกเว้น admin/owner
- รับรถเป็นเหตุการณ์ที่นำจำนวนสินค้าที่มาถึงเข้าคิวสาขา
- พิมพ์เลขท้ายบิลแล้วกด Enter ต้องเลือกบิลโดยไม่เลื่อนหน้าจอ เพื่อยิงรายการต่อเนื่อง
- ส่งสินค้าแบบบางส่วนได้ โดยจำนวนส่งห้ามเกินจำนวนที่รับเข้าสาขาและยังไม่ส่ง
- เงินสดปลายทางจัดการในโมดูลเก็บเงิน ไม่บังคับให้ workflow ส่งสินค้ารับเงินเสร็จในหน้าจอเดียว

## Dashboards And Dates

- Dashboard เดิมของกรุงเทพยังคงอยู่ และ Dashboard งานขึ้นรถเป็นอีกหน้าหนึ่ง
- Dashboard สาขาปลายทางแยกยอดรับเข้า ค้างส่ง รวมทั้งหมด ส่งวันนี้ และยอดเก็บเงินสดปลายทาง
- KPI บริษัทนับอายุจากวันเปิดบิล ส่วนมุมมองสาขาสามารถเลือกนับจากวันรับรถ
- รูปแบบวันที่สำหรับการแสดงผลคือ `dd/mm/yy`
- สาขาและรหัสเส้นทางใน dashboard ต้องดึงจากการตั้งค่าบริษัท ไม่ hard-code รายชื่อสาขา

## Concurrency And Performance

- เลขบิล การสร้าง master ที่อาจชนกัน และการจัดสรรบิลเข้าเที่ยวต้องใช้ atomic RPC หรือ constraint ที่รองรับ conflict
- ห้ามใช้ลำดับ read-then-insert โดยไม่มี conflict handling
- ห้าม Realtime หรือการ save จากเครื่องอื่น reset ฟอร์มเปิดบิลของผู้ใช้
- หลังบันทึกสำเร็จให้อัปเดต state เฉพาะส่วนทันที และ sync ส่วนอื่นเบื้องหลัง
- ป้องกัน double submit ขณะกำลังบันทึก
- การโหลดช้าเป็น defect สำคัญ ต้องตรวจ query/RPC timing ก่อนเพิ่ม timeout

## Data Safety

- เก็บ snapshot ชื่อและข้อมูลสำคัญในธุรกรรมเพื่อไม่ให้บิลเก่าเปลี่ยนตาม master
- ประวัติราคาและเอกสารธุรกรรมใช้ version/cancel/reverse ไม่ hard delete
- ลบความสัมพันธ์ได้โดยไม่ลบข้อมูล master
- ห้ามเก็บ secrets, keys หรือรหัสผ่านใน Git
